## Full Finding Register

### CRIT-001: InputSanitizationMiddleware Corrupts Passwords [FIXED]

**File**: `backend/app/Http/Middleware/InputSanitizationMiddleware.php`  
**OWASP**: A02:2021 (Cryptographic Failures)  
**CVSS**: 9.1 (Critical)

**Issue**: Middleware runs `htmlspecialchars()` and `strip_tags()` on ALL incoming request data, including `password` and `password_confirmation` fields. If a user has `&` or `<` in their password (valid characters per most policies), the password gets silently mutated before hashing — user registers with one password but can never log in. The middleware is registered globally in the HTTP kernel.

**Fix**: Skip `password`, `password_confirmation`, `current_password` fields from sanitization. Applied.

### CRIT-002: SQL Injection via Unvalidated Filter Parameter [FIXED]

**File**: `backend/app/Http/Controllers/Api/V1/UserController.php:21`  
**OWASP**: A03:2021 (Injection)  
**CVSS**: 8.6 (High)

**Issue**: `$request->role` is passed directly to `where('role', $role)` without whitelist validation. While Eloquent parameterizes the value, the column is fixed (`role`), making this a limited injection — but an attacker can still probe valid role values via timing differences.

**Fix**: Added whitelist validation for `role` parameter. Applied.

### CRIT-003: Partner Webhook Missing Authentication [FIXED]

**File**: `backend/routes/api.php:72`  
**OWASP**: A01:2021 (Broken Access Control)  
**CVSS**: 9.8 (Critical)

**Issue**: `POST /api/v1/webhooks/partner/order` has no `webhook.ip` middleware and no signature verification. The `receiveOrder` method creates deliveries directly. Any attacker who discovers this endpoint can create arbitrary delivery orders. The `orderStatus` endpoint does have `verifyWebhookSignature`, creating an inconsistent security posture.

**Fix**: Added `webhook.ip:partner` middleware to partner webhook routes. Applied.

### CRIT-004: Stored XSS via Socket Chat Messages [FIXED]

**File**: `socket-server/src/handlers/chat.js:64-72`  
**OWASP**: A03:2021 (Injection)  
**CVSS**: 8.3 (High)

**Issue**: Chat messages are stored in Redis and broadcast to all ride participants without any HTML sanitization. A malicious rider or driver can inject HTML/JS into chat messages that would render if displayed in a WebView or rich text component.

**Fix**: Added server-side text sanitization (strip HTML tags from message content before storing/broadcasting). Applied.

### HIGH-001: No Pagination Limits on List Endpoints [FIXED]

**File**: Multiple controllers  
**OWASP**: A05:2021 (Security Misconfiguration)  
**CVSS**: 7.5 (High)

**Issue**: Controllers accept `$request->per_page ?? 15` without upper bounds. An attacker can request `per_page=100000` causing massive DB queries and potential OOM.

**Fix**: Capped `per_page` at 100 across all list endpoints. Applied.

### HIGH-002: Socket.IO CORS Misconfiguration

**File**: `socket-server/src/index.js:25-28`  
**CVSS**: 7.4 (High)

**Issue**: CORS origin is set to `config.clientUrl` which defaults to `http://localhost:8000`. In production, this should be restricted to the actual mobile app origin. The `methods: ['GET', 'POST']` is also overly permissive — socket.IO only needs GET/POST for handshake.

### HIGH-003: Social Auth State Parameter Missing

**File**: `backend/app/Http/Controllers/Api/V1/Auth/SocialAuthController.php`  
**CVSS**: 7.3 (High)

**Issue**: The social auth callback uses `stateless()` and does not validate the `state` parameter, making it vulnerable to CSRF-style social login attacks. An attacker can trick a victim into linking their social account to an attacker-controlled EasyRyde account.

### HIGH-004: Socket Auth Validation Error Leaks User Info

**File**: `socket-server/src/services/auth.js:70-77`  
**CVSS**: 6.8 (Medium-High)

**Issue**: Error messages reveal whether a token is malformed, expired, unauthorized, or from a different Sanctum format. An attacker can enumerate valid token formats via error messages.

### HIGH-005: Account Enumeration via Forgot Password

**File**: `backend/app/Http/Controllers/Api/V1/AuthController.php:160-169`  
**CVSS**: 6.5 (Medium-High)

**Issue**: Different response messages for existing vs non-existing users (`password.user` vs `passwords.sent`). This allows account enumeration.

### HIGH-006: Race Condition in Wallet Pending Balance

**File**: `backend/app/Services/WalletService.php:404-428`  
**CVSS**: 7.0 (High)

**Issue**: `pendingTopUp` increments `pending_balance` in a separate transaction and uses the transaction ID as the gateway reference. Under high concurrency, multiple pending top-ups could be created for the same wallet without balance consistency checks.

### HIGH-007: Mobile API Token Seed Shows Fallback URL

**File**: `mobile/packages/shared/src/api/client.ts:5`  
**CVSS**: 6.2 (Medium)

**Issue**: Default `API_BASE` is `http://127.0.0.1:8000/api`. If `EXPO_PUBLIC_API_URL` env var is not set in production build, the app will silently use localhost. No build-time validation of API URL.

### MEDIUM-001: Soft Deletes Not Fully Leveraged

**File**: `backend/app/Http/Controllers/Api/V1/UserController.php:69`  
**CVSS**: 5.4 (Medium)

**Issue**: User model has `SoftDeletes` trait but the destroy method calls `$user->delete()` which does apply soft delete. However, related data (rides, payments, wallets) is not anonymized, leaving PII in related tables.

### MEDIUM-002: Socket Rate Limits Are In-Memory

**File**: `socket-server/src/middleware/rateLimit.js`  
**CVSS**: 5.0 (Medium)

**Issue**: Rate limit windows are stored in a local `Map` — not shared via Redis. With multiple socket server instances (horizontal scaling), each instance has independent counters.

### MEDIUM-003: No Input Size Limits on Upload Endpoints

**File**: `backend/app/Http/Controllers/Api/V1/KycController.php`  
**CVSS**: 5.3 (Medium)

**Issue**: KYC document uploads have no explicit file size limits beyond PHP config. An attacker could upload massive files.

### MEDIUM-004: Redis Auth Token Cache Shared Across Instances

**File**: `socket-server/src/services/auth.js:16-18`  
**CVSS**: 4.8 (Medium)

**Issue**: Token cache key is `auth:token:<plaintext>`. If Redis is compromised, all active token caches are readable.

### MEDIUM-005: CashPaymentService Not Audited

**File**: `backend/app/Services/CashPaymentService.php`  
**CVSS**: 4.0 (Medium)

**Issue**: Cash payments bypass gateway verification entirely. No trip confirmation photo or proof-of-collection for cash rides.

## Payment Flow Audit

### PayFast
- ✅ ITN verification present via `verifyItn()` in `PayFastService`
- ✅ IP whitelist on webhook endpoint
- ❌ No replay protection (idempotency_key used inconsistently)
- ❌ `payfastReturn` endpoint is public and returns payment status — information leak

### Ozow
- ✅ Webhook signature verification via `verifyWebhook()` 
- ✅ IP whitelist on webhook endpoint
- ❌ Transaction reference doubles as internal payment ID — could be guessed
- ❌ Status check uses loose `strtolower` comparison — could be manipulated

### Stripe
- ✅ Webhook signature verification via `Stripe\Webhook::constructEvent()`
- ✅ Payment intent creation with amount validation
- ❌ No `webhook.ip:stripe` middleware applied (but signature verification provides equivalent protection)

### Wallet
- ✅ Redis-locked debit operations prevent race conditions
- ✅ Consistent lock ordering for transfers
- ✅ Idempotency keys on payment creation
- ❌ `pendingTopUp` increments pending_balance before gateway confirmation
- ❌ Withdrawal request creates immediate debit — should hold in pending state
